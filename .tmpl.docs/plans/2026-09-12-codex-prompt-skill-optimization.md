# Codex Prompt／Skill 最佳化：共識與驗收方向

日期：2026-09-12。狀態：Q1–Q7 與整體共識已確認；使用者以「開始修改」授權執行。修改與驗收結果見 [維護歷程](../history/2026-09-12-codex-prompt-skill-optimization.md)。

## 目標與範圍

提高 Codex 的執行效率，同時維持治理遵循與完整交付。全面盤點專案 Skill 的 description 與共用入口；首批改善 `AGENTS.md`、runtime 文件、Codex Agent 指令，以及需求訪談、spec、實作與 review 的核心 Skill。其他專用 Skill 有具體問題才納入。

保留九階段流程、既有人工確認點、四軸審查、兩輪上限、TDD 與證據要求。改善規則的適用條件、重複表達、按需載入與完成邊界，不以模型會自行驗證為由移除治理要求。

Claude 相關設定與角色檔案不在修改範圍。共用 Skill 維持一份核心指引；CC／Codex 前綴表示使用環境。Codex 專屬差異採條件式參考文件或 Codex 設定，避免將模型特有建議無條件套用到 Claude。Claude 文件只用於相容性檢查，不要求 Claude 模型實測。

範本術語見 [CONTEXT.md](../CONTEXT.md)。Playbook／關卡 Agent 的產品定義不加入通用範本。保留專案 placeholder 與既有未提交變更。

## 工作順序

1. 保存修改前的完整輸入範圍與固定案例，盤點觸發條件、重複指令、工具假設及完成邊界。把可核對的文件問題與模型行為假設分開。
2. 將候選對應到最小修改與驗收案例。優先處理 WIP review 範圍、過度要求篇幅、固定探索方式與指定工具造成的阻塞。
3. 在保留治理要求的前提下，修改共用指引與 Codex 專屬指引，維持來源紀錄及既有 Skill 同步契約。同步共用內容不代表調整 Claude 專屬設定。
4. 執行結構檢查與 Codex 固定案例比較，整理每項變更的證據、限制與未驗證處。沒有實測證據的項目只報告文件改善，不宣稱模型效能提升。

## 六類行為驗收

下表落實 Q7 的案例類型；具體 fixture 與模型執行條件在修改前固定。這不是已完成的測試報告。

| 類型 | 觀察情境 | 必須維持的行為 |
| --- | --- | --- |
| 小幅文件修改 | 明確的小範圍文字修正 | 完整修正，保留原意與無關內容；只載入適用規則。 |
| 需求訪談 | 含可查事實、已確認決策與相依問題的需求 | 自行查事實；不重問已確認事項；尊重問題相依與最終共識確認。 |
| Spec | 有多個行為及邊界的已確認需求 | Spec 與 traceability 完整，不以篇幅或任意 seam 數量取代覆蓋要求。 |
| WIP review | Committed、staged、unstaged、untracked 及無變更情境 | 正確界定並涵蓋指定範圍；證據對應實際版本；不把未審查說成通過。 |
| 實作驗證 | 已核准範圍與測試計畫，含需修正的失敗 | 遵守 TDD 與既定驗收，完成必要修正；不擴張工作或重複索取既有授權。 |
| 等價工具替代 | 指定工具不可用，但有等價能力或完全無替代能力 | 能提供等價證據才替代；無法驗證時明確回報，不假稱完成。 |

## 證據與成效

修改前後使用相同任務、fixture、模型、effort 與工具條件；需互動的案例使用固定回覆。先檢查治理與交付品質，再比較讀檔、工具呼叫、重複確認與可取得的 token／時間。無法取得的量測明列未知；文字長度不充當 token 量測。有限案例只能支持該樣本的觀察。

`python3 scripts/verify-project.py` 與 `python3 -m unittest discover -s tests -v` 驗證範本結構及既有回歸測試；與實際 Codex 行為比較分開報告。既有未提交變更造成的失敗也需另行歸因。

若驗收發現必須改變已保留的治理要求，回到該項決策討論；不把治理變動包裝成文字精簡。
